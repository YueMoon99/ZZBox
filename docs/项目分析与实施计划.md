# GPU 视频重编码工具（Windows / NVENC）项目分析与实施计划

> 目标：做一款 Windows 端视频重编码软件，支持 NVIDIA NVENC 硬件加速、质量/码率双模式、按比例缩放、批量队列、音频抽取与音轨删除。

---

## 一、小丸工具箱是否开源？

**结论：半开源，且已停止维护，不适合作为代码基座。**

| 项目 | 状态 | 说明 |
|---|---|---|
| 原版小丸工具箱 GUI | 源码曾在 GitHub 公开（`wljcom/marukotoolbox`，Apache-2.0） | 停留在 2015 年，.NET Framework 4.0 + WinForms，代码量大且结构混乱 |
| 官方发行版 | 免费但**非完全开源** | 打包内含 neroAAC 等非自由组件，2019 年后停更 |
| 开源内核 | 是 | x264 / FFmpeg / MP4Box / neroAAC 本身就是开源项目，小丸只是给它们做的 GUI 壳 |
| MarukoToolBox-Rewrite | **完全开源**（Python + Tkinter + FFmpeg） | 社区重制版，功能覆盖度高，可读性好，是目前最接近的参考实现 |

**关键判断**：小丸工具箱本质是 "FFmpeg 命令行 + 参数面板"，它的价值在交互设计而非技术壁垒。想加 GPU 加速，改老代码的成本远高于重写一个壳（0.5～1 天就能跑通核心链路）。所以建议**参考它的交互，不复用它的代码**。

## 二、整体难度评估

**总量：中等偏低（对熟悉 FFmpeg 的开发者）～ 中等（对不熟悉的人）。**

难点不在"编码"，而在三件事：**参数映射的准确性**、**队列的健壮性**、**GPU 管线的完整性**。真正的编码能力 FFmpeg 已经全部提供。

| 功能 | 难度 | 工作量（单人） | 主要坑 |
|---|---|---|---|
| FFmpeg 封装 + 进度解析 | 低 | 1 天 | `-progress pipe:1` 是流式键值对，需按 `out_time_us` 算百分比，别用 `-stats` 抓 stderr |
| CRF / 恒定码率双模式 | **中** | 2 天 | **NVENC 没有 CRF**，必须用 CQ 模拟并对数值做校准（见下） |
| 分辨率 + 百分比缩放（25/50/100/200%） | 低-中 | 1 天 | 宽高必须取偶数（`-2`）；不能放大超过源；非方形像素（SAR）要归一 |
| 批量队列 | 中 | 3 天 | 进程生命周期、取消/暂停、失败重试、任务持久化、输出名冲突 |
| 音频抽取 | 低 | 0.5 天 | MP4 里 AAC 直接 copy 成 m4a 最快；抽 MP3 必须重编码 |
| 删除 / 选择音轨 | 低 | 1 天 | 必须显式 `-map`，默认流选择会漏轨；容器兼容性（opus/flac/pcm 进不了 MP4） |
| 全 GPU 管线（硬解 + GPU 缩放） | 中-高 | 3 天 | 色彩空间、10bit、HDR 元数据、`scale_cuda` 格式协商 |
| 打包分发 + 驱动/显卡检测 | 中 | 2 天 | ffmpeg.exe 体积（~80MB）、NVENC 可用性探测、杀软误报 |

**MVP 可用版本：3～4 周（全职）/ 1.5～2 个月（业余）。**

## 三、最大的技术陷阱：NVENC 没有 CRF

这是整个项目最容易被做错、也最影响口碑的一点。

- `libx264/libx265` 的 `-crf` 是**感知质量因子**：逐帧逐块自适应调整 QP（mb-tree、AQ、心理视觉优化）。
- `NVENC` 只有 `-cq`（恒定质量提示）和 `-qp`（恒定 QP，完全不自适应）。**同样的数字，画质不对等，文件通常大 10%～15%。**

正确写法（`-b:v 0` 绝对不能漏，否则会退回默认 2Mbps 目标码率，`-cq` 被压制，画质直接崩）：

```
-c:v hevc_nvenc -preset p6 -tune hq -rc vbr -cq 22 -b:v 0 \
-spatial-aq 1 -aq-strength 8 -rc-lookahead 20 \
-multipass qres -b_ref_mode middle
```

`spatial-aq / rc-lookahead / multipass / b_ref_mode` 这四项是"用速度换画质"的关键开关，全开后能追回大部分差距。

**建议的产品设计**：
1. UI 上仍显示 CRF 滑块（用户认知习惯），内部做映射：`cq ≈ crf − 2`，再由实测校准表覆盖。
2. 提供"画质优先（CPU）/ 速度优先（GPU）"一个开关，让用户自己选，而不是假装 GPU 画质等于 CPU。
3. 首次运行做一次 10 秒片段的自动校准（对比文件大小与 VMAF），把映射写进配置——这是能拉开差距的功能点。

## 四、技术选型

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **C# WPF / .NET 8（推荐）** | Windows 原生、进程管理顺手、单文件发布、UI 控件成熟 | 只能 Windows | 本项目首选 |
| Tauri + Rust/React | 体积小（~10MB）、界面现代 | 需要前端栈，进程/编码逻辑要多写一层 | 想要好看 UI |
| Python + PySide6 | 出原型最快（3 天见界面） | 打包 100MB+、无类型保障 | 先验证想法 |
| Electron | 生态最全 | 体积 150MB+，杀软敏感 | 不推荐 |

**统一原则：FFmpeg 作为独立子进程调用，不做库内链接。** 理由：
- 崩溃隔离（一个坏文件不会带崩整个 App）
- 进度、取消、优先级都好控
- 避开 FFmpeg `--enable-nonfree`（NVENC 编译所需）导致的 GPL 传染与再分发许可问题

## 五、架构

```
┌───────────────────────────────────────────────┐
│  UI 层（WPF / MVVM）                          │
│  参数面板 · 队列列表 · 进度 · 预设管理        │
└──────────────────┬────────────────────────────┘
                   │ 命令 / 状态（INotifyPropertyChanged）
┌──────────────────▼────────────────────────────┐
│  应用层                                        │
│  JobQueue（并发度=1~2）· JobRunner · 重试策略  │
└──────────────────┬────────────────────────────┘
                   │ 参数对象 → 命令行参数数组
┌──────────────────▼────────────────────────────┐
│  编码层                                        │
│  FfprobeService（媒体信息）                    │
│  CommandBuilder（参数 → argv）                 │
│  ProcessRunner（异步读 stdout/stderr）         │
│  ProgressParser（-progress → 百分比/速度/ETA） │
└──────────────────┬────────────────────────────┘
                   │
              ffmpeg.exe（含 NVENC）
```

**关键工程约束**：
- 参数用 `List<string>` 逐项拼接，**绝不拼接字符串**（中文路径、空格、引号是 Windows 上最常见的崩溃源）。
- 队列串行执行（并发 1）。GeForce 卡有并发编码会话上限（新驱动约 8 个），并发跑反而抢显存、降低总吞吐。
- 任务状态落盘（JSON），程序崩溃后能恢复队列。

## 六、关键命令模板

**1. 全 GPU 管线转码（1080p → 720p，HEVC）**
```
ffmpeg -hwaccel cuda -hwaccel_output_format cuda -i in.mp4 \
  -vf "scale_cuda=w=-2:h=720" \
  -c:v hevc_nvenc -preset p6 -tune hq -rc vbr -cq 22 -b:v 0 \
  -spatial-aq 1 -rc-lookahead 20 -multipass qres \
  -map 0:v:0 -map 0:a? -c:a copy -map_metadata 0 \
  -movflags +faststart -progress pipe:1 -nostats out.mp4
```

**2. 恒定码率模式**
```
-c:v h264_nvenc -rc cbr -b:v 6M -maxrate 6M -bufsize 12M
```

**3. 抽取音频**
```
ffmpeg -i in.mp4 -vn -map 0:a:0 -c:a copy out.m4a      # AAC 直接 copy，秒出
ffmpeg -i in.mp4 -vn -map 0:a:0 -c:a libmp3lame -b:a 192k out.mp3
```

**4. 删除指定音轨 / 只保留第一条音轨**
```
ffmpeg -i in.mp4 -map 0:v -map 0:a:0 -c copy out.mp4
```

**5. 媒体信息（JSON）**
```
ffprobe -v quiet -print_format json -show_format -show_streams in.mp4
```
→ 解析 `streams[].codec_type / width / height / sample_aspect_ratio / channels`，驱动 UI 的音轨列表与缩放上限。

## 七、分阶段计划

### M0 · 技术验证（1～2 天）
- [ ] 下载带 NVENC 的 ffmpeg 静态构建，确认 `ffmpeg -encoders | grep nvenc` 有输出
- [ ] `nvidia-smi` 读显卡型号与驱动版本，建立"最低驱动 → 可用编码器"对照表
- [ ] 跑 1080p / 4K 各一段，测：CQ 18/22/26 三档的文件大小、编码速度（fps/speed）、肉眼画质
- [ ] **产出：CRF↔CQ 映射校准表**（后续直接进产品）

### M1 · 单文件转码 MVP（4～5 天）
- [ ] 拖放导入 + ffprobe 读元信息
- [ ] 编码器下拉（H.264/HEVC/AV1，按显卡能力过滤）
- [ ] 质量模式：CRF 滑块 / 码率输入（自动换算 kbps）
- [ ] 缩放：百分比（25/50/100/200）+ 自定义宽高 + "保持比例"锁
- [ ] 进度条、速度、ETA、剩余时间
- [ ] **验收：任选一个 1080p 文件，UI 设置 → 输出可播放且参数正确**

### M2 · 批量队列（3～4 天）
- [ ] 多文件入队、拖拽排序、批量套用同一套参数
- [ ] 队列串行执行、单任务取消、整队暂停/继续
- [ ] 失败重试（1 次）+ 失败原因展示（stderr 尾部 20 行）
- [ ] 输出命名规则、目标目录、同名冲突策略（覆盖/跳过/加序号）
- [ ] 队列状态持久化
- [ ] **验收：拖 20 个文件进去无人值守跑完，中途取消任一任务不影响后续**

### M3 · 音频与音轨（2 天）
- [ ] 音轨列表（语言、声道、码率、编码格式）
- [ ] 抽取：原格式 copy / 转 AAC / 转 MP3
- [ ] 删除音轨、只留指定音轨、多音轨保留
- [ ] 容器兼容性校验（opus/flac 进 MP4 → 提示转 AAC 或改 MKV）
- [ ] "仅封装不重编码"模式（`-c copy`，秒级完成）

### M4 · 全 GPU 管线与兼容性（3～4 天）
- [ ] 硬件解码开关（CUDA / D3D11VA），失败自动回退软解
- [ ] `scale_cuda` 全显存管线；不支持时降级 CPU scale（并提示速度损失）
- [ ] 10bit / HDR 元数据透传（`-pix_fmt p010le`、色彩原色/传递特性、mastering display）
- [ ] 显卡能力探测：无 N 卡 / 驱动过旧 / 编码器不支持 → 精确提示并回退 libx264
- [ ] **验收：4K HDR 源 → 1080p SDR 或 HDR 输出，色彩不偏、不泛白**

### M5 · 产品化（3～4 天）
- [ ] 预设管理（导入/导出 JSON，内置"B站投稿""微信压缩""存档"）
- [ ] 单文件发布（self-contained）、安装包（Inno Setup / MSIX）
- [ ] 首次运行环境自检、日志文件、崩溃捕获
- [ ] 可选：GPU 占用监控、缩略图预览、VMAF 质量对比

**总计：约 17～23 个工作日。**

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **CQ ≠ CRF，用户按老经验填 CRF 23 结果画质变差** | 高（口碑直接受损） | 内置校准表 + 明确的"GPU 模式画质略低"提示 + 首次校准 |
| 漏写 `-b:v 0` | 高（画质崩溃且难排查） | 参数构建器里做成强制项，单元测试断言 |
| 色彩/HDR 处理不当，输出偏色 | 中-高 | 优先 `-map_metadata 0` + 显式色彩参数；M4 单独验收 |
| GeForce 并发会话限制 / 显存不足 | 中 | 队列串行，并发度可配但默认 1 |
| ffmpeg 含 NVENC 需 `--enable-nonfree`，GPL 再分发受限 | 中 | 子进程调用（独立程序）；或引导用户自行下载 ffmpeg；商用需法务确认 |
| 中文/空格路径、特殊字符导致进程启动失败 | 中 | 全程 `ArgumentList` 逐项传参，禁用字符串拼接 |
| 杀软误报（自解压 + 调用 ffmpeg） | 低-中 | 代码签名、避免加壳、用官方 NSIS/Inno |
| 显卡型号差异（Pascal 无 B 帧参考、Ada 才有 AV1） | 中 | 启动时探测能力矩阵，UI 按能力禁用选项 |

## 九、竞品与差异化

现有工具已覆盖 80% 需求：**HandBrake**（开源、质量最佳、批量队列、NVENC）、**ShanaEncoder**（免费、NVENC/QSV/AMF、批量、中文）、**XMedia Recode**（参数最全）。

单靠"支持 NVENC + 批量"没有竞争力。可打的差异点：

1. **小丸式的极简交互**——一屏搞定，不堆砌 60 个参数（HandBrake 的最大劝退点）
2. **百分比缩放预设**（25/50/100/200%）——现有工具都要手填宽高或选分辨率，这个交互确实缺
3. **CRF↔CQ 自动校准**——别人都不做，做出来就是技术壁垒
4. **纯绿色免安装 + 中文** + 拖进去就压，零学习成本
5. **音频抽取 / 删轨 / 仅封装** 集成在同一界面，不用开第二个软件

## 十、建议的第一步

不要先做 UI。**先写一个 30 行的命令行脚本**，把你最关心的三个场景跑通：

1. 1080p H.264 → HEVC NVENC CQ 22，测速 + 看画质
2. 同一文件 → x265 CRF 22，对比文件大小
3. 5120×2880 → 按 50% 缩放，检查是否为 2560×1440、比例是否失真

这三个结果会直接决定产品形态（画质差距是否可接受、缩放逻辑是否要特殊处理）。跑完再动手搭框架。
